Which changes can skip senior review?

Three routing policies replayed on a year of pull requests to Orchard Core, a public multi-tenant .NET CMS. For each: how many changes that later broke something it let through, and how much work it sent to a senior.

Changes judged
479 pull requests merged in 2025

11 changes with a confirmed later breakage
Outcomes observed until
26 September 2026

What each policy let through, for the work it sent to a senior

A path list and a deterministic diff reader each let 7 of the 11 through while sending a third of all changes to a senior. Sending a random third would let about 7 through. The hybrid, which lets a model read what the structural rules cannot, let 2 of 11 through for 35%.

95% intervals, treating the 11 as independent: 31% to 89% of such failures pass for the first two, 2% to 52% for the hybrid. The 11 are 11 distinct defects. On them, the hybrid escalated 5 that the deterministic policy passed, and never the reverse (sign test on 5 discordant cases, p = 0.06). With 11 incomplete attributions added (22 cases), 14, 12 and 5 passed. Two of the hybrid's reviews are UNKNOWN: the model answered in a malformed way, and UNKNOWN never passes.

One it caught, one it missed

#18541 Add missing useCdn in ScriptBlock

Hybrid sent it to a senior

What the gate saw, at merge on 11 November 2025

One file, the Liquid script block: a switch reformatted over 27 added lines, with one new case.

  case "useCdn":
+     name = (await argument.Expression.EvaluateAsync(context)).ToStringValue();
      break;
  • Path listPassed
  • Deterministic, no structural signalPassed
  • Hybrid, model risk 3 of 5Senior

The model's reason: “The new "useCdn" case incorrectly assigns to the 'name' variable instead of introducing/using a useCdn variable, so the CDN flag is never actually applied while silently overwriting 'name' if both attributes are used together.”

What was learned later

Reverted the same day by a maintainer:

“… resetting is the right choice, as a new error was introduced by it.”

#18542, 11 November 2025

#18508 Properly register KeyManagementOptions for protection-data

All three let it pass

What the gate saw, at merge on 30 October 2025

Nine added lines in the Azure and Redis data protection startups, including:

+ services.RemoveAll<IConfigureOptions<KeyManagementOptions>>();
  services.AddTransient<IConfigureOptions<KeyManagementOptions>,
      RedisKeyManagementOptionsSetup>();
  • Path listPassed
  • Deterministic, no structural signalPassed
  • Hybrid, model risk 2 of 5Passed

The model's reason named the mechanism and still rated it low: “could subtly change behavior if another feature also registers KeyManagementOptions setups that were relied upon.”

What was learned later

Twelve weeks on, sites with Redis data protection failed to start with a NullReferenceException. The fix:

“Fixes a regression introduced by PR #18508. For Redis, the existing IConfigureOptions<KeyManagementOptions> must not be removed, because it is being altered by the RedisKeyManagementOptionsSetup.”

#18731, 22 January 2026

Removing registrations is a structural fact. The deterministic rule only watched deleted registration lines, not an added call that deletes them: a gap a rule can close.

What this does not show

  • Eleven cases are few. The intervals are wide, and the difference between hybrid and rules rests on 5 cases.
  • An unlabelled change is not a safe change. The labels only know failures someone later tied to their cause: a merged revert with a stated defect, or an attribution by a maintainer or in the merged fix, checked against the files. Weaker attributions are the 22-case line.
  • The model may remember. Most of these failures were public before its training cutoff (January 2026). Its reasons cite the diff, and the four failures first reported after the cutoff, all from the 22-case line, were all sent to a senior, but only a run on new pull requests settles it.
  • No test coverage was available. Missing coverage is unknown, not zero.
  • A detected migration is not a safe migration. Orchard Core migrates with YesSql, not EF, and separates tenants by table prefix or database; the rules detect those changes, they do not prove them safe.
  • Passing this gate is not merging. Real auto-merge also depends on tests, required reviews and branch rules.

Run it on your own policy

The cohort manifest, the labels with their evidence and exclusions, the three policies, every decision with its reason and the model's raw answers are in the repository.

A policy is one function, decide(snapshot, diff), returning ALLOW, REVIEW_REQUIRED or UNKNOWN. The replayer scores it against the same 479 changes and 11 failures.

The deterministic policy also runs as a required GitHub check that fails closed. It judges the pull request with the policy from the base branch, never the one in the pull request, and only a named senior can release it, for that exact commit: see it on a change to an authorization check.

The model read 357 of the 479 changes: 372 calls to Claude Sonnet 5, 3.1 million tokens in, 86 thousand out.
